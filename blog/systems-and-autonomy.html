Automation Is Not Evidence

October 27, 2026 · Robert Foley · Essay

A job can finish. A dashboard can stay green. A report can say “zero anomalies.” None of those statements, by itself, proves that the underlying data was fresh or that the result was correct.

I learned that the hard way: one of my sports-picks pipelines kept running against frozen data for 34 days before I found the break in the input path. The automation was active. The feedback loop was not.

Execution and outcome are different facts

“The scheduled task ran” is evidence about execution. “The input was current” is a separate claim. “The result was correct” is another. When those get collapsed into one green check, a quiet failure can look like success.

The same distinction matters in research. A test vector reproduced is not a challenge solved. A runner and protocol are not completed metrics. A target written down is not a result achieved.

Make the status legible

For any system I depend on, I want to know when it last received valid input, what it processed, what it produced, and whether anyone checked the output. If data is stale or a required step fails, the system should say so clearly instead of manufacturing a reassuring “all clear.”

I also try to label work honestly:

  • Planned: intended, but not yet run.
  • Probed: a limited experiment or test vector; not a full validation.
  • Reported: an observed result with a stated scope and time window.
  • Verified: another person or repeatable check can confirm the evidence.

Autonomy needs boundaries

Automation is useful when it removes repetitive work and makes the remaining decisions clearer. It should not quietly turn uncertainty into authority. I want consequential external actions to have an explicit approval boundary, and I want a record of what happened after an action—not just a record that a model or script was invoked.

More agents do not automatically mean less work. If nobody can tell what ran, what it relied on, and what changed, the system has added another thing to supervise. Reliability is earned by observable inputs, honest failure states, and outcomes that can be checked.

That is the standard I am trying to build toward: not “the automation ran,” but “here is what it used, here is what happened, and here is how we know.”
